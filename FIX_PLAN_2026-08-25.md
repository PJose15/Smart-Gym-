# Nexera Comprehensive Fix Plan — 2026-08-25

Derived from `AUDIT_2026-08-25.md` (16 CRITICAL · 34 HIGH · ~60 MEDIUM · ~55 LOW, all criticals adversarially verified).

## Decisions baked into this plan
- **Environment: pre-launch / test data.** Migrations may be aggressive — drop/recreate policies, revoke grants, reset views, reseed flags freely. No production data-migration protocol required. We still write idempotent, ordered migrations and run each on a Supabase branch before merge, but we do **not** need backward-compat shims or data backfills for existing rows.
- **Workout data model: recommendation to be approved** (see Stage 4 analysis — proposal is *consolidate on `workout_sessions` in lbs*).
- **AI model: `gemini-2.5-flash`,** wired as an env var (`GEMINI_MODEL`) with `gemini-2.5-flash` as the default, so it can be changed without a code change.
- **Execution: plan-only.** Nothing below is implemented yet. Each stage is presented for your approval; schema/auth/billing-touching stages get an explicit checkpoint before I write code.

## Guiding principles
1. **Sequence by unblock value.** Security migrations and auth unification come first because they either close takeover-grade holes or unblock the entire user journey that everything else depends on.
2. **Batch migrations.** All new SQL lands as migrations **034–03x**, one migration per coherent concern, never re-editing shipped migrations 001–033.
3. **Every fix ships with a test.** The audit's core lesson is that green tests hid runtime breakage because nothing exercised schema/RLS/contracts. Each stage adds the missing coverage for what it touches.
4. **Hold the conventions** (from CLAUDE.md): `gen_random_uuid()`, INSERT policies use `WITH CHECK`, every table gets RLS + `updated_at` trigger, new FKs get indexes, member routes use `verifyMember` + own-tenant binding, staff via `useStaffAuth`, weights stored in lbs and displayed via `lib/weight.ts`, feed rebuilt via `formatFeedEvent`, DOC_18 color tokens only, a11y roles/labels.
5. **Verify each stage before moving on:** `tsc` clean ×5 workspaces, targeted test suite green, and — because tests don't hit the DB — a **live smoke check via Supabase MCP** (run the actual query/policy against a branch) for every schema/RLS fix.

## Stage dependency graph
```
Stage 1 (security migrations) ─┐
Stage 2 (auth unification) ─────┼─> Stage 5 (tenant-binding API) ─> Stage 6 (correctness/UX) ─> Stage 7 (hardening + tests + deps)
Stage 3 (schema-drift repair) ─┤
Stage 4 (dead-wiring + workout model) ┘
```
Stages 1–4 are largely independent and could be worked in parallel; 5 depends on 1+3; 6 depends on 2; 7 is last.

# STAGE 1 — Security migration wave  🔒 CHECKPOINT before execution
**Goal:** close every takeover/cross-tenant hole at the database layer. All are small, single-migration fixes. **Migration 034_security_hardening.sql** (may split into 2–3 if cleaner).

| # | Finding | Change |
|---|---------|--------|
| SEC-C1 | Self-promote to super_admin (`001:1099`) | Drop `users_own_profile`; recreate as separate `FOR SELECT` + `FOR UPDATE` policies where UPDATE `WITH CHECK (id = auth.uid() AND platform_role = (SELECT platform_role FROM users WHERE id = auth.uid()))`. Add a `BEFORE UPDATE` trigger on `users` that rejects `platform_role`/`gym_id` changes from non-service-role as defense-in-depth. |
| SEC-C2 | Program tables world-writable (`017`/`020`) | `DROP POLICY IF EXISTS service_role_programs ON programs;` (+ the 3 siblings). Service role bypasses RLS, so no replacement needed. Verify the 020 correctly-scoped policies remain. |
| SEC-C3 | Views writable → RLS bypass | `REVOKE INSERT, UPDATE, DELETE ON profiles, gym_members FROM authenticated, anon;` Keep SELECT (032 already scopes it). If the mobile auth upsert path needs profile self-write, add a scoped `SECURITY DEFINER` RPC `upsert_own_profile()` instead of the view write. |
| DB-H1 | feed_reactions/comments impersonation (`001:1261`) | Drop the two `FOR ALL` gym-scoped policies; recreate: `FOR SELECT USING (is_gym_member(gym_of_event))`, and `FOR INSERT/UPDATE/DELETE` with `WITH CHECK/USING (member_id IN (SELECT id FROM members WHERE user_id = auth.uid()))`. |
| DB-H2 | trainer_messages forgery (`001:1384`) | Split member policy: SELECT on own thread; INSERT `WITH CHECK (sender_type='member' AND member_id IN own)`; UPDATE limited to `read_at` via column-guard trigger or a dedicated RPC. |
| DB-H3 | Client-writable PR/volume fields | Once mobile writes through the API (Stage 4/5), tighten `sessions_own` INSERT/UPDATE to exclude direct writes of `is_personal_best`/`pr_improvement_*`/`total_volume_lbs` (trigger validation), OR revoke direct table write and force the `/api/sessions` path. **Ordering:** land after Stage 5 so mobile isn't cut off first. |
| DB-H6 | challenge score tampering (`001:1295`) | Split `challenge_participants_own`: SELECT + INSERT `WITH CHECK (member_id own AND gym matches challenge)`; score/rank UPDATE service-role only. |
| BE-H6 (DB side) | auth/lookup PII + anon table exposure | `REVOKE SELECT ON gyms, machines FROM anon;` expose a column-limited `public_gym_landing` / `public_machine_landing` view for the QR flow (id, name, slug, logo only). |
| M-3 (026 grants) | Blanket GRANT ALL + anon default privileges | New migration narrowing `authenticated` to `SELECT, INSERT, UPDATE, DELETE` (drop TRUNCATE/REFERENCES) and dropping the `ALTER DEFAULT PRIVILEGES … TO anon` so future tables aren't anon-readable by default. |
| H-1 (leaderboard) | get_leaderboard DEFINER cross-gym | Add `IF NOT is_gym_member(p_gym_id) THEN RAISE …` guard inside the function (033 redefinition). *(Verifier downgraded impact to LOW — uuid+points only — but the guard is a 2-line add, include it here.)* |

**Tests/verification:** Add `supabase/tests/rls_security.test.ts` (or SQL-based checks run via MCP against a branch) proving: a member JWT **cannot** UPDATE `platform_role`, cannot write another member's reaction, cannot DELETE `gym_members`, cannot read another gym's programs, anon cannot SELECT `gyms`. This is the highest-value new test file in the whole plan.

**Risk:** DB-H3 could break mobile writes if landed before Stage 5 — sequenced accordingly.

**Workout data-model decision (recommendation for your approval):**
> **Recommend: consolidate on `workout_sessions` (lbs) as the single canonical store.**
> Rationale: the entire read/derive stack already depends on it — readiness cache, muscle-map, Performance DNA, feed generation, home, web progress/profile, and all session-complete side effects read `workout_sessions`; conventions store lbs. The mobile `workouts`/`workout_sets` model (kg) feeds only mobile's own progress/profile and duplicates the concept. Since we're pre-launch (no data to migrate), the cheapest correct move is: **mobile writes to `workout_sessions` (converting kg→lbs at the boundary) via the same `/api/sessions` path the scan flow uses, and mobile progress/profile read `workout_sessions`.** Retire `workouts`/`workout_exercises`/`sets` (or keep as an optional normalized detail linked to a session if per-set granularity is needed for analytics — decide during Stage 4 planning). This also resolves IN-M3 (unit source of truth → `member_settings.weight_unit`), IN-M6 (dual models), M-3 mobile weight display, and MB-H1 points (writes go through the API which can award points server-side).
> **This is the one item I want explicit sign-off on before building** — it's the largest single refactor and reshapes mobile's logging screen.

**Tests:** flag-seeding assertion; cron registration check; a Gemini live-call smoke (one real request per action) to confirm 2.5-flash responds; web-push subscribe→send loopback; tier-gate rejection test.
