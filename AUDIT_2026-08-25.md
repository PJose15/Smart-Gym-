# Nexera Full-Stack Audit — 2026-08-25

**Scope:** 8 parallel specialized audits (backend API ×135 routes, database ×33 migrations/82 tables, member web UI, staff web UI, mobile Expo app, AI operations, full-stack integration contracts, build/test health) followed by an adversarial verification pass on every CRITICAL finding (3 independent verifier agents, tasked to refute). All findings below the CRITICAL tier were evidence-checked by the original auditors against current code; all CRITICAL findings were additionally re-verified and **all survived refutation**.

**Headline:** the codebase compiles clean, builds clean, and passes all 1,230 tests — but a significant amount of **shipped surface is silently broken at runtime** because tests never exercise the DB schema, RLS policies, or cross-layer contracts. The dominant failure modes are:

1. **Schema drift** — code (staff pages, mobile badge/points services, readiness log) querying tables/columns/RPCs that don't exist.
2. **Tenant-binding gaps** — auth proves *identity* but ~a dozen routes/policies never bind caller-supplied `gym_id`/`event_id`/`session_id` to the caller's tenant.
3. **Dead wiring** — features fully built on both ends but never connected (web push, offline sync, tier gating, check-in scheduler, Tailwind pipeline, mobile feature flags).

**Totals: 16 CRITICAL · 34 HIGH · ~60 MEDIUM · ~55 LOW** (deduplicated across audits).

## PART 1 — CRITICAL (all adversarially verified ✅)

### SEC-C1. Any authenticated user can self-promote to `super_admin` ✅ VERIFIED
- `supabase/migrations/001_nexera_schema.sql:1099` — `users_own_profile FOR ALL USING (id = auth.uid())`, no `WITH CHECK`, `platform_role` CHECK allows `'super_admin'`, and migration 026 granted `ALL ON ALL TABLES TO authenticated`.
- Any member: `PATCH /rest/v1/users?id=eq.<self> {"platform_role":"super_admin"}` → unlocks every `is_super_admin()` policy (users, gyms, error_log, feature_flags, admin logs…). Full platform takeover.
- No later migration fixes it (verified exhaustively 002–033).
- **Fix:** split into SELECT + UPDATE policies with `WITH CHECK` freezing `platform_role`, or trigger-guard the column; also narrow 026's blanket grant.

### SEC-C2. Program tables world-read/writable — 020's policy drop targeted the wrong names ✅ VERIFIED
- 017 created `service_role_programs` etc. as `FOR ALL USING(true) WITH CHECK(true)` on `programs`, `program_days`, `program_exercises`, `member_program_assignments`. 020 dropped `programs_all` etc. — names that never existed (`IF EXISTS` = silent no-op).
- Any authenticated user (any gym) — and anon for SELECT — can read/insert/update/delete every gym's programs and member assignments.
- **Fix:** one migration dropping the four `service_role_*` policies (service_role bypasses RLS anyway).

### SEC-C3. `profiles`/`gym_members` views are owner-rights AND writable → RLS-bypassing UPDATE/DELETE on `users`/`members` ✅ VERIFIED
- Views (021, redefined 032) are auto-updatable, run with owner rights (032 set `security_invoker` only on `sets`/`badges`/`member_badges`), no `WITH CHECK OPTION`; 032 revoked only anon SELECT — authenticated keeps INSERT/UPDATE/DELETE from 026.
- Any member can UPDATE any member's score/status in their gym, rewrite other users' email/name via `profiles`, or `DELETE /rest/v1/gym_members?gym_id=eq.<gym>` — **deleting the gym's `members` rows and cascading away all workout data**. (Verifier note: `profiles` does not expose `platform_role`, so this is data tampering/destruction, not privilege escalation.)
- **Fix:** `REVOKE INSERT, UPDATE, DELETE ON profiles, gym_members FROM authenticated` (restore self-writes via scoped RPC if the mobile auth upsert needs it).

### INT-C1. Scan-flow phone-OTP never establishes a session — the core product loop 401s ✅ VERIFIED
- `api/auth/verify/route.ts` runs `verifyOtp` on the service-role client, **discards the session**, returns member JSON only; `AuthOTP.tsx` stores it in `scanFlowStore`; no cookies, no `setSession`, no Bearer headers anywhere in `app/m/**`.
- Every downstream call (`/api/sessions`, `pr-check`, `[id]/complete`, `scan-events`, `programs/active`, `members/onboard`, `day-complete`) requires a cookie session → **401 for every scan-onboarded member**. Flow only works if the browser already has a session from a separate email login.
- (The Aug 4–5 walkthrough verified the *mobile* app with email/password demo auth — it never covered this path.)
- Compounded by **INT-H6**: `/auth` is email+password only, so phone-OTP members have *no* working authenticated surface at all.
- **Fix:** return the session tokens from `/api/auth/verify` and `supabase.auth.setSession()` client-side (or verify OTP through the SSR cookie client).

### WEB-C1. Challenge detail page crashes on every visit ✅ VERIFIED (mechanism corrected)
- `(member)/gym/challenges/[challengeId]/page.tsx:41` — `use(params)` with `params: Promise<…>` is Next-15 style. On Next 14.2.35 params is a plain object; the vendored React canary's `use()` throws "unsupported type" → unconditional crash into the (unstyled, see WEB-C2) error boundary.
- **Fix:** `{ params }: { params: { challengeId: string } }` and read directly.

### WEB-C2. Tailwind is never generated — 27 files render unstyled, including all 5 error boundaries ✅ VERIFIED
- `tailwind.config.ts` + `@tailwindcss/postcss` exist but **no CSS file contains `@import "tailwindcss"` / `@tailwind` directives** → zero utilities emitted.
- Affected: all 8 `components/muscleMap/*` (Profile → Body Map tab), 11 `components/checkIn/*` (incl. live `CheckInMessage`), 3 `components/readiness/*`, and `app/error.tsx` + all 4 surface `error.tsx` boundaries.
- **Fix:** add the Tailwind v4 entry to `globals.css` (and align the v3-style config), or convert those components to token inline styles.

### STAFF-C1. Two disjoint auth systems — root admin surface needs a double login ✅ VERIFIED
- `lib/supabase.ts` uses `createClient` from `@supabase/supabase-js` (**localStorage, no cookies**; session set only at `/auth`). Staff APIs use `@supabase/ssr` **cookie** sessions set only by `/api/auth/staff/signin`.
- The 5 root pages calling `useStaffAuth` (dashboard, analytics, assignments, members, copilot) sit inside `AuthGate` (localStorage) → they require **both** sessions. Cookie-only owners bounce to `/auth`; localStorage-only users bounce to `/staff/login`. Sidebar "Owner Dashboard" and SetupChecklist "/machines" links are dead paths.
- **Fix:** switch `lib/supabase.ts` to `createBrowserClient` from `@supabase/ssr` (one cookie session for both), or gate the root surface on the cookie check only.

### STAFF-C2. Co-Pilot + Assignments permanently "not enabled" — feature_flags columns don't exist ✅ VERIFIED
- Both query `.select('enabled').eq('key','ai_trainer_copilot').is('profile_id', null)`; table has `flag_key`/`is_enabled`, no `profile_id`. Query errors → `false` forever. Bonus: `ai_trainer_copilot` is never seeded anywhere.
- **Fix:** `.select('is_enabled').eq('flag_key','ai_trainer_copilot').maybeSingle()` + seed the flag.

### STAFF-C3. `gym_members` view has no `role` column — Members page broken, Add Member dead ✅ VERIFIED
- `members/page.tsx:310,391`, `assignments/page.tsx:142`, `programs/[id]/page.tsx:111` select/filter/insert `role` on the view (columns: id, gym_id, profile_id, smartgym_score, onboarding_status, joined_at, created_at).
- **Fix:** join role from `gym_memberships` (add to view or query it directly); route Add Member through an API.

### STAFF-C4. Safety Alerts page permanently errors — 4 of 7 selected columns don't exist ✅ VERIFIED
- `members/discomfort/page.tsx:106` selects `gym_id, full_name, unstable_count_7d, last_discomfort_at` — none exist on `feedback_discomfort_summary`. **And** RLS is own-rows-only, so even a fixed query shows staff nothing.
- **Fix:** align columns + serve via a staff API route (service role, gym-scoped).

### MOB-C1. All 15 mobile feature-flag keys unseeded — push, streaks, badges, leaderboard, and every AI feature permanently OFF ✅ VERIFIED
- `featureFlags.ts` returns `false` for missing keys; the 15 keys mobile checks have **zero overlap** with the 7 seeded keys (e.g. mobile `push_notifications` vs seeded `push_notifications_enabled`). Admin UI is update-only — it *cannot* create the rows.
- **Fix:** seeding migration mapping mobile keys (or rename mobile keys to the seeded ones).

### MOB-C2. Mobile badge feature fully schema-broken ✅ VERIFIED
- `badgeService.ts` queries `slug`, `sort_order`, `gym_id` on the `badges` view and `profile_id`, `badge_id`, `unlocked_at` on `member_badges` — none exist (022/032). Every call 400s (errors swallowed). Home badge card also reads `icon_emoji`/`name` (view has `icon_name`/`title`).
- **Fix:** rewrite badgeService against `achievement_definitions`/`member_achievements` real columns (or extend the views with aliases + fix the upsert path).

### MOB-C3. `get_machine_by_slug` RPC doesn't exist — mobile QR scan dead-ends ✅ VERIFIED
- Only the caller + a hand-written type exist (which even disagree on the arg name: `slug` vs `slug_param`). No fallback query.
- **Fix:** create the RPC in a migration, or fall back to `.from('machines').eq('qr_slug', slug)`.

### AI-C1. Weekly check-in generation and the 48h auto-send deadline are never scheduled ✅ VERIFIED
- No pg_cron entry, vercel cron, workflow, or in-repo caller hits `/api/agents/checkin-generate` or `/api/cron/checkin-deadline` (all 9 cron-bearing migrations enumerated). `agent-daily` only *alerts* on overdue check-ins; it never sends.
- Also: 001 schedules edge functions `scheduled-daily`/`scheduled-weekly` that **don't exist**, and 006 schedules `/api/cron/readiness-recompute` which **doesn't exist** (AI-H4).
- **Fix:** migration adding the two schedules (Sunday generation per gym; daily deadline sweep); create-or-delete the phantom cron targets.

### AI-C2. `ai-generate` edge function: cross-member tip-cache poisoning + open prompt injection ✅ VERIFIED
- Any authenticated user can call `coaching_tip` with an arbitrary `member_id` and attacker-controlled `machine_name`/`muscle_groups` (interpolated raw into the Gemini prompt); the result is upserted into `ai_tip_cache` under the **victim's** member_id via service role, and `tips/route.ts` serves it back to the victim.
- **Fix:** resolve member from the caller's JWT; validate machine against DB; delimit user strings in prompts.

### AI-C3. All three Gemini clients hardcode retired model `gemini-1.5-flash` ✅ VERIFIED
- `geminiProvider.ts:23`, `generateCheckIn.ts:70`, `ai-generate/index.ts:22`. No env override wired. Gemini 1.5 Flash is retired → calls 404 and **every AI feature silently rides its template fallback with zero alerting**. (Run one live call to confirm, then treat as an outage.)
- **Fix:** bump to a current model (e.g. `gemini-2.0-flash`), make it env-configurable, log fallback activations.
